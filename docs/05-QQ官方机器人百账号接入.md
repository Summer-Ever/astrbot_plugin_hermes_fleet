# QQ 官方机器人 × 100 账号：真实接入路径

> 前一份 `04-百账号部署与隔离.md` 里那张对比表把 QQ 个人号（NapCat）当成了
> QQ 的主路径，于是得出"100 个号 = 100 个端口 + 100 个 NapCat 进程 + 100 次
> 扫码"的重运维结论。**那对你并不适用**——你用的是 QQ 官方机器人，
> 它走的是官方 WebSocket 长连接，没有本地端口、不需要扫码、不需要第三方
> 协议端。那份文档的隔离结论仍然成立，但部署成本那一节请以本文为准。
>
> 依据全部来自 AstrBot 源码 `astrbot/core/platform/sources/qqofficial/`，
> 引用处标了文件。凡是没验证的，明确写"未验证"。

## 1. 500 字结论

100 个 QQ 官方机器人 = **100 个 appid + 100 个 secret**，在一个 AstrBot 实例里
配 100 项 `qq_official` 适配器。每项占一条到 `api.sgroup.qq.com` 的 WebSocket
连接。没有本地端口、没有扫码、没有协议端进程。

由此带来三个直接后果：

1. **运维成本从"重"变成"中"**——真正的成本在向 QQ 开放平台申请 100 个
   机器人（实名、审核、配额），不在服务器上。
2. **隔离反而更简单**——`openid` 本身就是 per-bot 的，同一个真人在 A 号和
   B 号面前是两个不同的 id，天然不可能串。
3. **但 `openid` 也是 per-group 的**，所以"跨群同一个人"无法自动识别。
   这决定了身份模型不能用 QQ 号做主键（见 §3）。

## 2. 一个实例配 100 个账号，代码层面确认可行

`config["platform"]` 是**列表**，每项独立配置，AstrBot 逐一实例化适配器。
`qq_official` 适配器的元数据是：

```python
# astrbot/core/platform/sources/qqofficial/qqofficial_platform_adapter.py
def meta(self) -> PlatformMetadata:
    return PlatformMetadata(
        name="qq_official",
        description="QQ 机器人官方 API 适配器",
        id=cast(str, self.config.get("id")),
        support_proactive_message=True,
    )
```

`id` 就是你在面板里给每个账号起的名字（`qq-01`、`bot-alice`……）。
插件用 `event.get_platform_id()` 拿到它，直接作为记忆库的路由键。

面板里每一项大致是：

```json
{
  "type": "qq_official",
  "id": "qq-01",
  "enable": true,
  "appid": "102xxxxx",
  "secret": "xxxxxx",
  "enable_group_c2c": true,
  "enable_guild_direct_message": false,
  "use_markdown": true
}
```

`appid` / `secret` 是**强制读取**（`platform_config["appid"]`），缺了会抛
`KeyError` 让该适配器起不来。`use_markdown` 有默认值 `true`，旧配置没写也能跑。

> **未验证**：面板的适配器列表页在 100 项规模下的操作体验（滚动、搜索、
> 批量导入配置）。AstrBot 是否支持从配置文件直接粘贴 100 项，需要你实测一次。
> 如果面板卡，可以编辑 `data/cmd_config.json` 的 `platform` 数组再重启。

## 3. `openid` 的真相：这是本插件最重要的一个约束

hermes_core 的 `_scope_keys` 里有一段作者实测留下的注释，值得逐字读：

> QQ 官方适配器中 `sender_id` 是 `member_openid`(群) / `user_openid`(私聊)，
> 并非 QQ 号；且 `member_openid` 按群维度不同、与 `user_openid` 不同命名空间。

展开成三条事实：

| 场景 | `sender_id` 是什么 | 是否稳定 |
|---|---|---|
| 私聊 | `user_openid` | 同一个 bot 下稳定 |
| 群聊 | `member_openid` | **按群不同**，同一个群内稳定 |
| 换一个 bot | 全部重新分配 | 与上一个 bot 的 id 无关联 |

**所以"这个人昨天在群里说的事，今天私聊问他"在 id 层面是两个人。**
这不是插件缺陷，是 QQ 的设计。

本插件的处理方式是**不猜**：`IdentityStore.resolve()` 默认一个 openid 就是
一个人，只有在显式 `link()` 过之后才归一。宁可把一个人当成两个，也不要
把两个人当成一个——后者会让 A 的记忆出现在 B 面前的对话里，是事故。

要跨群认人，只有两条路：让用户在群里自报身份（然后手工 `link`），
或者干脆不认（推荐：群记忆保持在本群上下文中，本来就该如此）。

## 4. 官方消息限制对记忆系统的影响

`qq_official` 适配器里没有自己实现限流，它是被协议规则约束的：

- **被动回复**必须带 `msg_id`（适配器会缓存最近一条，`_session_last_message_id`）。
- 群 / 频道在 `msg_id` 缺失且不允许主动推送时**直接跳过发送**并打 warning。
- 私聊发送时会 `payload.pop("msg_id")`，因为私聊主动推送限制相对宽松。
- 媒体消息降级为 `msg_type=7` 并去掉 markdown；markdown 失败会回退纯文本重试。

对"记忆系统"的具体含义：

1. **不能靠"主动提醒"来补偿记忆**。记忆的价值必须体现在"用户说话时我答得对"，
   而不是"我到点推送一条"。群里的主动消息配额很紧，用它做记忆召回不划算。
2. **总结必须是离线后台任务**，不能挂在用户请求上。一次总结要调模型、
   可能几秒到几十秒，而被动回复窗口有限。
3. **`msg_id` 缓存是会话级的**，重启即丢。重启后第一条群消息之前不要尝试
   主动发消息——适配器会跳过并记 warning，不会报错，容易被误判为"插件没反应"。

> **未验证**：QQ 开放平台对不同主体的 100 个机器人的具体配额（主动消息条数、
> API 调用频率、可加入群数上限）。这些数字会变，且有按主体/按 bot 的区别，
> 我不在这里编造。上线前请以开放平台后台的实时配额为准。

## 5. 资源估算

单个 `qq_official` 适配器 = 一个 `botpy` 客户端 + 一条 WebSocket。
100 个账号就是 100 条长连接、100 份心跳。

| 项 | 估算 | 说明 |
|---|---|---|
| WebSocket 连接 | 100 条 | 每条一个心跳定时器 |
| 记忆库文件描述符 | ≤ `max_open_bots`（默认 24） | 其余按 LRU 关闭，冷启动 7.6ms |
| 磁盘 | 每账号每 10 万条消息约 40–80 MB | 含 FTS5 trigram 索引，膨胀 3.84 倍 |

> **未验证**：单进程 100 个 `botpy` 客户端的实际内存占用与事件循环延迟，
> 以及 100 条连接同时断线重连时的表现（"重连风暴"）。这是本方案最大的
> 未知项，建议按 10 → 30 → 100 三档压测：每档跑 24 小时，看
> `event loop lag` 与 RSS 增长曲线。如果 100 档扛不住，退路是
> **按 20–30 个账号分实例**，记忆库目录通过 `bot_db_dir` 指向同一处
> （但 SQLite 不支持跨机共享文件系统，分实例必须同机）。

## 6. 上线步骤

```bash
# 1. 装插件
cd <AstrBot>/data/plugins
git clone https://github.com/Summer-Ever/astrbot_plugin_hermes_fleet.git
```

2. 面板里逐个添加 `qq_official` 适配器，**`id` 用可读的命名**（`qq-01`…`qq-100`）。
   这个名字就是记忆库的路由键，改成别的等于换了一个记忆库。

3. 插件设置里确认：
   - `bot_db_dir` 留空（用默认）或指向一个**本地磁盘**目录
     （WAL 放 NFS/SMB 是错误用法，100 个库尤其不能）
   - `max_open_bots` 保持 24；账号数少可以调低

4. 用 `/fleet 我是谁` 验证路由：应显示正确的 `platform id` 与场景。

5. 用 `/fleet 状态` 看库目录和文件数，确认每个账号落到**不同**的 `.db`。

6. 分别在两个账号里说同一句话，确认 `/fleet 状态` 的记忆条数各自独立增长。

## 7. 会翻车的地方（按概率排序）

| 风险 | 表现 | 对策 |
|---|---|---|
| 向开放平台申请 100 个机器人 | 卡审核、实名额度、同主体数量限制 | 这是**最大**的实际瓶颈，先确认能拿到 20 个再谈 100 个 |
| 100 条连接的重连风暴 | 某一刻全部断线后同时重连，CPU 尖峰、部分账号长时间离线 | 未验证，需压测；必要时分批重启 |
| `id` 改动 | 记忆库"消失"（其实是换了文件） | `id` 一旦上线不要改；改名要做迁移 |
| 群 `member_openid` 按群变化 | 同一个人在 A 群和 B 群的记忆不共享 | 设计如此。需要共享就做显式 `link` |
| 100 个 bot 共用一个模型配额 | 总结任务排队跟不上 | 目前消息只落库不总结（见 README「当前状态」），接总结时必须先做令牌桶与预算 |
| 备份时只拷 `.db` | 最近的写入缺失 | 关停时插件会 `wal_checkpoint(TRUNCATE)`；运行中备份要连 `-wal` 一起拷，或用 `VACUUM INTO` |

## 8. 与 hermes_core 的差异（为什么不能直接用它跑 100 个号）

| 维度 | hermes_core | 本插件 |
|---|---|---|
| 隔离键 | `(owner_id, group_id)` | `platform_id` → 独立库文件 |
| 跨 bot 串号 | **会发生**：同一个人的私聊记忆会被另一个 bot 注入 | 物理上不可能 |
| 账号路由 | 无此概念 | `BotRegistry` + LRU |
| 插件内 SQL | 单连接 + 全局锁，全库视角 | 每库一连接，按账号分散写锁（p99 7.8ms vs 2288ms） |
| 业务代码位置 | `main.py`（3892 行） | `packages/fleet/`，不 import astrbot，可脱机测试 |
| 注入策略 | v1.2.0 起只注入常驻 | 沿用同一策略（理由见 README） |
| 总结/整理/技能 | 已实现 | **未实现**，下一步 |

可复用的部分已经搬过来了：`recall.py`（880 行纯函数）、六词条常驻模型、
工具措辞、注入去重与临时 content part 的做法。

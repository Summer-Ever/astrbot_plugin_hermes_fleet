# SQLite 能承载 100 bot 吗：实测结论

> 本文所有数字都是**本机实测**，不是估算。
> 环境：Windows / Python 3.13.14 / SQLite 3.53.1（FTS5 + trigram 可用）。
> 复现：`python benchmarks/bench_sqlite.py`、`bench_arch.py`、`bench_asyncio.py`。
> 换机器会有差异（尤其磁盘 fsync 性能），但量级关系不会反转。

## 结论

**能。而且余量大约 6000 倍。**

需求侧：100 bot × 300 轮/天 ≈ 6 万条/天 ≈ **0.7 条/秒**（峰值按 50 条/秒 留余量）。
实测能力：真实 `add_message` 路径（逐条提交 + FTS 触发器维护）**4,365 条/秒**。

真正的瓶颈**不是 SQLite**，而是访问模式。同一条 SQLite，换个用法，p99 从
2,288ms 变成 7.76ms——差 300 倍，但这 300 倍跟数据库引擎无关。

## 一、实测数据

### 1.1 写入

| 配置 | 吞吐（行/秒） |
|---|---|
| 逐条提交，`synchronous=FULL` | 1,409 |
| 逐条提交，`synchronous=NORMAL` | 18,344 |
| 每 50 条提交，NORMAL | 61,257 |
| 每 500 条提交，NORMAL | 159,806 |
| 每 500 条提交，NORMAL，带 FTS 触发器 | 143,391 |
| **真实 `HermesDB.add_message`（逐条 autocommit + FTS）** | **4,365** |

最后一行是唯一有意义的基线：它包含 hermes_core 的真实写入路径（含 FTS 索引维护）。
即便这样，仍是需求的 6000 倍。

### 1.2 检索

| 场景 | p50 | p95 | p99 |
|---|---|---|---|
| FTS5 trigram top-100，1 万行 | 0.033ms | 0.067ms | — |
| FTS5 trigram top-100，5 万行 | 0.05ms | 0.17ms | — |
| FTS5 + 元数据过滤，5 万行 | 0.08ms | 0.18ms | 0.35ms |
| 常驻词条读（`bot+owner+active`） | 0.01ms | 0.03ms | 0.07ms |
| 技能索引读 | 0.01ms | 0.01ms | 0.02ms |
| 8 读者 + 1 写者并发（WAL），读 | 1.84ms | 2.76ms | 3.14ms |

**注入路径的读 p99 在 0.35ms 以内。** 相比之下，一次 LLM 请求要几百毫秒到几秒。
检索不是瓶颈，哪怕数据量再涨一个数量级。

### 1.3 冷启动

2 万消息 + 4000 记忆：**7.6ms**（首次 10.7ms，含全部增量迁移 +
`_repair_orphan_private` + `_normalize_private_scope`）。

### 1.4 FTS5 trigram 的体积代价

2000 条记忆，平均 34.2 字：原始 **0.36MB** → 含 FTS 索引 **1.74MB**，**膨胀 3.84 倍**。

这是 3 字滑窗的必然代价（每个位置一个 trigram）。折算到 540 万条记忆约
2-4GB——**必须按这个数字规划磁盘**，不能按「文本长度 × 条数」估。

## 二、并发形态决定成败（最重要的一节）

同一台机器、同一个总负载（100 bot，合计 200 条/秒），只改「写者怎么组织」：

| 形态 | p50 | p95 | p99 | max |
|---|---|---|---|---|
| 单库 + 8 个写线程 | 0.35 | 102.6 | **433.8** | 874.8 |
| 单库 + 100 个写线程 | 0.30 | 970.6 | **2288.4** | 6118.3 |
| 单库 + 1 写线程（**只按条数触发提交**） | 3.23 | 513.0 | 517.0 | 519.8 |
| 单库 + 1 写线程（**条数或超时双触发**） | 3.23 | 68.1 | **74.8** | 75.2 |
| 每 bot 一库 + 100 线程 | 0.25 | 2.42 | **7.8** | 47.3 |

三条可直接落地的结论：

**结论 1：写者数量是尾延迟的唯一决定因素。**
100 个线程抢一个库，p99 = 2.3 秒。这不是 SQLite 慢，而是每个线程都要排队拿写锁，
排队时间随线程数线性恶化。换成 1 个写者，同样的吞吐，p99 掉到 75ms。

**结论 2：只按条数触发提交是陷阱。**
`commit_every=32` 遇上「每 0.5 秒来 100 条」的突发，每轮的余数（100 % 32 = 4）
要多等一个周期，稳定制造 500ms 尾延迟。改成「满 32 条 **或** 距上次提交超过
50ms，先到者触发」后，p99 从 517ms 降到 74.8ms。**这一条与数据库无关，但只有
压测才能发现**——它不会报错，只会让少数消息莫名其妙晚半秒。

**结论 3：单库单写者（75ms）与每 bot 一库（7.8ms）都能用。**
选哪个不是性能问题，是运维问题，见第四节。

## 三、必须改的配置（默认值不够）

```python
con = sqlite3.connect(path, isolation_level=None, timeout=30.0,
                      check_same_thread=False)
con.execute("pragma journal_mode=WAL")        # 读写不互相阻塞，这是并发的前提
con.execute("pragma synchronous=NORMAL")      # FULL 会让每次提交都等 fsync，慢 13 倍
con.execute("pragma busy_timeout=10000")      # 拿锁不是立刻失败，而是等
con.execute("pragma cache_size=-32000")       # 32MB，减少翻页
con.execute("pragma temp_store=MEMORY")       # 临时表进内存（FTS 排序会用到）
```

实测差距：`synchronous` 从 `FULL` 改 `NORMAL`，逐条写入从 1,409 涨到 18,344 条/秒
（13 倍）。代价是断电时可能丢最后一个事务——对聊天记忆完全可接受，因为原始消息
还能从平台重新拉。

WAL 的读不阻塞已被验证：8 个读者在 1 个写者持续写入时，读 p99 = 3.14ms。

## 四、单库还是每 bot 一库

| | 单库 + `bot_id` 列 | 每 bot 一库 |
|---|---|---|
| 尾延迟 | 75ms（1 写者） | 7.8ms |
| 备份 | 一次 `VACUUM INTO` | 100 次，要保证一致性快照 |
| 删除租户 | `DELETE WHERE bot_id=?` + `VACUUM`（大表很慢） | 删文件，瞬时 |
| 跨 bot 检索/统计 | 一条 SQL | 要自己聚合 100 个库 |
| 单点故障 | 一个库坏了全挂 | 只影响一个 bot |
| 迁移/加列 | 一次 | 100 次（可用同脚本批跑） |
| 文件数 | 3 | 300（db + wal + shm） |

**建议：先用单库 + `bot_id`，把写者收敛成 1 个。**

理由：100 个库的备份与迁移是长期负担，而 75ms 的落库延迟在异步链路上无感
（消息落库不阻塞回复）。等到某个 bot 的数据量真的到了需要独立的程度（比如单
bot 超过 500 万条），再把这个 bot 单独迁出去——因为表结构相同，迁移就是
`ATTACH` + `INSERT SELECT`。

**但如果你的写入是「多线程直接写库」而不是「单写者 + 队列」，那就必须每 bot 一库。**
这是二选一：要么改写入模型，要么改存储布局。不改任何一个，p99 就是 2 秒。

## 五、真的会翻车的场景（诚实边界）

以下情况 SQLite 不行，不要硬上：

1. **多个 AstrBot 实例共享一份记忆。** SQLite 的写锁只在单机文件系统内有效，
   WAL 在 NFS/SMB 上是错误用法（官方明确不支持）。100 个 bot 如果分布在
   多台机器、多个进程，就必须换 Postgres 或做服务化。
2. **需要在线备份 / 时间点恢复。** 有 `backup` API 和 `VACUUM INTO`，但做不到
   PITR，恢复粒度是「上一次快照」。
3. **摄入速度超过约 5000 条/秒且要求持久。** 批量写能到 15 万条/秒，但那是
   单写者串行的上限；再多就要分片。
4. **需要行级权限 / 审计日志 / 加密列。** SQLite 没有 RLS，加密要靠 SQLCipher
   （另一个构建，不是标准库）。
5. **运维要在线改数据。** 有人用 DB 工具开着事务不提交，会挡住整个写队列
   （`busy_timeout` 到了就失败）。

对 100 bot 聊天记忆这个具体场景：写入 0.7 条/秒、单机单进程、读多写少、
不需要 PITR——**一条都不沾**。所以 SQLite 是合理选择，不是将就。

## 六、代码在哪

`packages/storage_sqlite/` 是 `MemoryStore` 的 SQLite 实现，
跑通了契约包的全部 17 个一致性用例（`python run_tests.py -p storage_sqlite`）。

它和 hermes_core 的三处不同，都是本文数据支撑的：

1. **单连接 + 一把锁，同步执行，不用 `to_thread`。**
   注入读 p99 = 0.07ms，线程切换开销与之同量级，卸线程只会更慢。
2. **`add_many` 批量提交是主路径，`add` 是退化情形。**
3. **可见性只在 Python 调 `Memory.can_read`，不在 SQL 里重复拼条件。**
   代价是候选池开大（`limit × 8`），换「永远不会拼错 WHERE」。

## 七、上一轮说错的地方（更正）

| 上一轮的说法 | 实测 | 更正 |
|---|---|---|
| 「启动期全表扫描百万行不可控」 | 2 万条冷启动 **7.6ms**；真实查询走 `idx_mem_active` 索引，正常库返回 0 行 | **错了。** 那个 N+1 只在「有孤儿行」时触发，而孤儿行是个位数。启动路径不是问题 |
| 「`SELECT *` 最多捞 9000 行」 | 这是最坏情况（`if len(out) >= limit: break` 通常 1-2 层就够） | 结论（要重写检索）不变，但依据要说准 |
| 「单连接同步执行是头号硬伤」 | 单连接锁内同步读 p99 = **0.07ms** | **表述错了。** 慢的不是「同步」，是「多线程共享一个连接」+「没有批量提交」。锁内同步执行对这个负载是**正确**选择 |
| 「FTS trigram 索引 2-4 倍」 | 实测 **3.84 倍** | 当时的估算碰巧落在区间内，但现在有实测值，按 4 倍规划 |

第 1 条和第 3 条是实质性错误，会影响技术选型——如果按第 1 条判断，会去做
不必要的「版本化迁移脚本重构」（那件事本身有价值，但**不是性能问题**）。

# 100 个账号、记忆互不互通：部署形态与隔离方案

> **勘误（后续补充）**：本文 §"平台成本"一节把 QQ 个人号（NapCat）当成了
> QQ 的主路径，得出"100 个号 = 100 个端口 + 100 次扫码"的重运维结论。
> 实际采用的是 **QQ 官方机器人**，走官方 WebSocket，无本地端口、无需扫码。
> 部署成本请以 `05-QQ官方机器人百账号接入.md` 为准；
> **本文的隔离结论（每账号一库、openid 语义、路由方式）仍然成立。**

> 这份文档回答一个具体问题：要跑 100 个机器人账号，每个账号的记忆完全独立，
> 该怎么部署、怎么隔离存储。
>
> 所有关于 AstrBot 的结论都标了源码位置。凡是我没验证的，明确写"未验证"。

## 0. 先把术语说清楚

**「实例」= 一个 AstrBot 程序进程。**

判断方法：你打开几个 WebUI 面板？只有一个 `http://你的IP:6185`，就是单实例；
装了两份 AstrBot、两个端口两个面板，就是多实例。

你的 100 个账号，有两种放法：

| | 一个 AstrBot 里配 100 个账号 | 装 100 个 AstrBot，每个 1 个账号 |
|---|---|---|
| WebUI 面板 | 1 个，一处管理全部 | 100 个，改配置要改 100 次 |
| 内存占用 | 1 份（约几百 MB） | 100 份（几十 GB） |
| 账号数上限 | 无硬限制（配置是列表） | 受机器资源限制 |
| 存储隔离 | 要在插件里按账号路由 | 天然隔离（各进程各的库） |
| 运维复杂度 | 低 | 极高 |

**推荐前者。** 下面都按"一个 AstrBot + 100 个账号配置"来讲。

## 1. 关键事实：AstrBot 已经给了你「bot 维度」

这一节是全部方案的地基，所以我贴源码。

**① 平台配置是一个列表，每项有唯一的 `id`**

`astrbot/core/platform/manager.py`：

```python
self.platforms_config = config["platform"]      # 列表，不是单个对象

async def initialize(self) -> None:
    for platform in self.platforms_config:      # 逐个加载
        await self.load_platform(platform)

async def load_platform(self, platform_config: dict) -> None:
    platform_id = platform_config.get("id")     # 每项必带 id，为空则跳过
    ...
    self._inst_map[platform_config["id"]] = {...}
    self._start_platform_task(f"platform_{type}_{id}", inst)
```

所以 **一个 AstrBot 实例可以配置任意多个同类型账号**，靠 `id` 区分。
`id` 里不能有 `:` 或 `!`（会被替换成 `_`），实际用 `bot001`、`qq_main` 这类即可。

**② 这个 `id` 就是这个账号的身份标识**

`astrbot/core/platform/sources/aiocqhttp/aiocqhttp_platform_adapter.py`：

```python
self.metadata = PlatformMetadata(
    name="aiocqhttp",
    id=cast(str, self.config.get("id")),   # ← 就是配置里的那个 id
)
```

**③ 每条消息事件都能拿到它**

`astrbot/core/platform/astr_message_event.py`：

```python
self.session = MessageSession(platform_name=platform_meta.id, ...)
# unified_msg_origin 的格式：  <platform_id>:<message_type>:<session_id>

def get_platform_id(self):
    """获取这个事件所属的平台的 ID。
    NOTE: 用户可能会同时运行多个相同类型的平台适配器，但能确定的是 ID 是唯一的。"""
    return self.platform_meta.id

def get_self_id(self) -> str:
    """获取机器人自身的id。"""
    return getattr(self.message_obj, "self_id", "")
```

**结论：`event.get_platform_id()` 就是你要的「这是哪个机器人账号」。**
不需要改 AstrBot，不需要 patch，插件里直接能调。

### 顺带更正我之前的一个推断

我上一轮说「同一个用户在 bot A 私聊说的私事，会在 bot B 被注入」。
核实之后要分成两半：

- **消息表（`messages`）其实已经隔离了。** hermes_core 用 `unified_msg_origin`
  当 `session_id`，而 umo 第一段就是 `platform_id`。所以消息天然按账号分开。
- **记忆表（`memories`）和常驻表（`resident`）确实会串。** 它们的键是
  `(owner_id, group_id)` 和 `(owner_id, scope)`，没有人账号这一维。

所以「记忆串号」这个结论成立，但原因要落在 `memories` / `resident` 上，
不是 `messages`。这影响改造范围：**只需要动记忆和常驻，消息表不用动。**

## 2. 隔离方案：每个账号一个库文件

### 为什么不是「一个库加一列 bot_id」

两种做法都可行，但对「记忆绝对不互通」这个需求，**每账号一库是唯一能给出
物理保证的做法**：

| | 单库 + `bot_id` 列 | 每账号一库 |
|---|---|---|
| 隔离保证 | 靠每条 SQL 都记得 `WHERE bot_id=?` | **靠文件系统，不可能串** |
| 漏写条件的后果 | 静默泄露别人的记忆 | 不存在这种可能 |
| 删一个账号 | `DELETE ...` + `VACUUM`（大库很慢） | 删文件，瞬时 |
| 备份 | 一次 `VACUUM INTO` | 100 次（可脚本化） |
| 跨账号统计 | 一条 SQL | 要聚合 100 个库 |
| 实测尾延迟（100 账号并发写） | 75ms（单写者）/ 2288ms（多线程） | **7.8ms** |
| 新增一个账号 | 插一行 | 建一个文件（首次写入时自动建） |

数据来源：`docs/03-SQLite方案实测.md` 第二节。**每账号一库同时也是延迟最好的形态**，
因为它天然把写锁分散到 100 个文件上。

对一个「一个账号对应一个记忆，不互通」的产品需求，选"靠 SQL 条件保证隔离"
而不是"靠文件边界保证隔离"，是在给自己埋一个只会在深夜暴露的 bug。

### 库怎么命名、怎么路由

```
data/plugin_data/astrbot_plugin_hermes_multi/
├── bots/
│   ├── bot001.db        ← 账号在 WebUI 里的 platform id
│   ├── bot001.db-wal
│   ├── bot002.db
│   └── ...
└── registry.json        ← id -> 显示名/平台/创建时间（可选，纯展示用）
```

路由逻辑（插件里就一段）：

```python
def store_for(event) -> SqliteMemoryStore:
    bot_id = event.get_platform_id() or event.get_self_id() or "default"
    return registry.get_or_create(bot_id)   # 惰性创建 + LRU 缓存
```

要点：

- **`get_platform_id()` 优先，`get_self_id()` 兜底。** 前者是配置 id（稳定、
  可控），后者是平台侧账号 ID（QQ 号、TG bot id）。配置 id 更适合当文件名，
  但需要防路径穿越（`safe_join`）。
- **惰性创建。** 100 个库不要启动时全开，用到才建。实测每个库的连接开销
  是微秒级，第一次写入时建表即可。
- **连接池要封顶。** 100 个常开连接在 Windows 上没问题（实测 100 线程 100 库
  跑满 p99 7.8ms），但如果一个实例可能挂几百个账号，就要 LRU 淘汰
  idle 超过 N 分钟的连接。

## 3. 真正的坑不在代码，在「100 个账号从哪来」

这是我认为你最该先确认的事。不同的平台，成本差一个量级：

| 平台 | 100 个账号需要什么 | 是否需要本机端口 | 现实难度 |
|---|---|---|---|
| **Telegram** | 100 个 bot token（找 @BotFather 批量建，几分钟一个） | 否（长轮询或 webhook） | 低 |
| **QQ 官方机器人** | 100 个 appid + secret（企业/个人主体申请，有审核） | 否（websocket 主动连接） | 中，卡在审核与配额 |
| **QQ 个人号（aiocqhttp/NapCat）** | 100 个 QQ 号 + 100 个 NapCat 实例 + **100 个不同端口** | **是，每个端口一个** | 高，且封号风险大 |
| **微信个人号** | 同上，且协议端更不稳定 | 是 | 很高 |
| **企业微信** | 100 个应用（同一企业下可建多个） | 否（回调或主动） | 中低 |

**关键差异：aiocqhttp 适配器是「反向 WebSocket 服务器」**，每个实例 `run()`
都在监听自己配置的 `ws_reverse_host:ws_reverse_port`（默认 6199）。
`astrbot/core/platform/sources/aiocqhttp/aiocqhttp_platform_adapter.py` 里：

```python
self.host = platform_config["ws_reverse_host"]
self.port = platform_config["ws_reverse_port"]
...
coro = self.bot.run_task(host=self.host, port=int(self.port), ...)
```

所以 **100 个 QQ 个人号 = 100 个端口 + 100 个 NapCat 进程 + 100 次扫码登录**。
这是运维灾难，与记忆系统无关，但会直接决定项目能不能落地。

Telegram 走的是主动连接，100 个 token 可以共用同一个进程、零本地端口。
**如果平台可以选，先做 Telegram 验证整套记忆系统，再上 QQ。**

## 4. 代码改造清单

在 `hermes-platform` 里，这件事落成一个新包 `hermes_botregistry`：

1. `BotStoreRegistry`：`get_or_create(platform_id) -> MemoryStore`，内含
   连接 LRU（上限可配，默认 128）、惰性建库、`close_all()`。
2. `ResidentStore` 同样按 bot 路由（可以同一个库文件，不同表）。
3. 采集侧插件（`astrbot_hermes_client`）在 `on_llm_request` 里：
   `store = registry.get_or_create(event.get_platform_id())`。
4. `purge_bot(platform_id)`：直接删库文件 + 从 registry 移除。比 `DELETE` 干净。
5. 备份脚本：遍历 `bots/*.db`，对每个执行 `VACUUM INTO`（保证一致性快照）。

要改而**不需要**改的：

- `Memory` 实体不用加 `bot_id` 字段（一个库只有一个 bot，字段是冗余的）。
  但 `hermes_contracts` 里已有 `bot_id`，保留它作为**冗余校验**：写库前断言
  它等于库所属的 bot，不等就报错。这能抓住"路由错库"这类 bug。
- `messages` 表结构不用动（umo 已含 platform_id）。

## 5. 未验证 / 需要你实测

1. **WebUI 能否顺利配 100 个平台适配器。** 配置层是列表，逻辑上无上限；
   但面板的渲染性能、以及 100 个适配器同时 `run()` 时的资源占用，我没法
   在这台机器上验证。建议先配 10 个跑通，再线性加到 100。
2. **100 个 aiocqhttp 实例的端口与文件句柄。** 理论上每个占 1 个端口 + 若干 fd。
   Windows 默认临时端口范围约 1.6 万个，100 个够用，但要避开已被占用的段。
3. **单进程 100 adapter 的事件循环延迟。** 这是我在上一份文档里就标记的未知项。
   100 个 adapter 意味着 100 个长驻协程 + 各自的 websocket 连接；记忆检索本身
   只占 0.07ms，但整个循环的调度开销要实测。**建议做 10/30/100 三档压测再定。**
4. 每个平台适配器的 `get_platform_id()` 是否都返回配置 id。我只核实了
   aiocqhttp。其他 adapter 大致同构（都传 `self.config.get("id")`），
   但建议在代码里做兜底：`get_platform_id() or get_self_id() or platform_name`。

## 6. 一句话总结

你的需求（100 个账号、记忆互不互通）**恰好是 SQLite 最擅长的形态**：
每账号一个库文件，写锁天然分散（实测 p99 7.8ms），隔离由文件系统保证而不是
SQL 条件，删账号等于删文件。

AstrBot 的 `platform_id` 已经把「这是哪个账号」送到你手上，不需要改框架。
真正要先解决的是**账号来源与平台选择**——那是运维问题，但会决定这个项目
能不能真的跑起 100 个。

# 与 hermes_core 的模块对照

这份文档回答一个具体问题：**fleet 到底照搬了 hermes_core 的什么，漏了什么，
哪些是刻意不做。** 逐项给行数和判定，避免"看起来都有了"的错觉。

判定分三档：

- **照搬设计**：沿用 core 的字段/表/交互约定，实现重写（因为要适配一 bot 一库）
- **重写**：同一个问题，解法不同
- **未做**：core 有，fleet 没有

---

## 1. 总表

| 模块 | hermes_core | hermes_fleet | 判定 |
|---|---|---|---|
| 常驻记忆 | `resident` 表 + `RESIDENT_BLOCKS` 六席（`db.py`） | `ResidentBlock` 六席 + `set_resident` | **照搬设计** |
| 记忆检索 | `modules/recall.py` 880 行 | `hermes_recall` 1006 行（整份搬迁 + v0.3.0 重写排序） | 搬迁 + 重写 |
| 记忆存储 | `modules/db.py` 2062 行，单库 | `store.py` 474 + `botdb.py` 430，**一 bot 一库** | **重写** |
| 模型路由 | `modules/router.py` 904 行，跟随全局默认模型 | `fallback.py` 380 行 + `chain.py` 显式链，与主应用解耦 | **重写（v0.7 解耦）** |
| WebUI | `views/hermes/` 2769 行 + `webapi.py` 959 行（7 tab / 30 接口） | `views/fleet/` 6 文件 + `webapi.py` 20 接口（全局 3 页 + 单账号 4 tab） | **重写（不照搬 tab 结构）** |
| 技能系统 | `modules/skill_hub.py` 322 行 + 4 个工具 | **无** | 刻意不做 |
| 热重载 | `hot_reload.py` 155 行 | **无** | 未做 |
| 后台总结/整理 | 散在 `main.py` 里 | `hermes_workers` 四个模块 + 契约解耦 | **重写** |
| 插件入口 | `main.py` 3892 行 | `main.py` 660 行 | **重写** |

## 2. 常驻记忆：设计照搬，实现重写

**照搬的部分**（有意为之，不是抄懒）：

- **六个封闭词条**：`address` / `assistant` / `user` / `preference` / `style` / `rules`。
  core 的 README 记过一次真实教训——按"条数"分配预算时，6 个槽位里 2 个被
  同一句"叫哥哥"占满，用户信息、偏好、避雷全被挤掉。改成固定槽位、整段覆盖后
  规模天然有界（最多 6 × 4KB），空槽不注入，注入成本可预测。这条经验直接继承。
- **顺序即注入顺序**：`address` 必须最前，否则会出现叫错人的体感问题。
- **整段覆盖而非追加**：`update_resident` 是覆盖语义，同一词条不会重复堆积。
- **作用域两态**：`private` 或 `group:<gid>`，没有 `global`。

**重写的部分**：

| | core | fleet | 为什么 |
|---|---|---|---|
| 存储 | 单库 `resident` 表 | 每 bot 一库，同表结构 | 账号隔离靠文件边界，不靠 WHERE |
| 作用域表示 | `str`（`"private"` / `"group:123"`） | `ResidentScope` dataclass | 避免 `str(scope)` 写出 `ResidentScope(kind='private')` 这种脏值 |
| 词条集合 | 模块级常量 | `StrEnum` | 类型检查能挡住拼错的词条名 |

**这一项确实是"照搬"，而且我承认**：常驻的六席划分、覆盖语义、顺序约定
都不是我重新想的。当初的取舍（固定槽位 vs 动态条目）已经被 core 用真实事故
验证过，重做一遍只会重踩。

## 3. WebUI：只做了第一页，其余仍未做

**core 有什么**：`views/hermes/app.js` 1844 行 + `index.html` 474 行 +
`style.css` 451 行，配 `webapi.py` 959 行（5 个 API 方法，均走
`Depends(require_plugin_scope)`），页面里能看记忆列表、常驻六席、整理日志、
模型调用记录。

**fleet 有什么**：`/fleet 状态`、`/fleet 我是谁`、`/fleet 总结`、`/fleet 清理`
四条聊天命令。**没有任何网页。**

### 为什么不能照搬

不是省事，是照搬会直接坏：

1. **数据模型不同。** core 的页面直接读那一张 `memories` 表。fleet 有 100 个
   库文件，页面得先选"哪个 bot"，再进单库视图；或者做跨库聚合。core 的
   `SELECT * FROM memories LIMIT 50` 在 fleet 里是"打开哪个库"的未定义问题。
2. **连接数会爆。** `BotRegistry` 的 LRU 上限默认 24 个打开句柄。一个"列出
   所有账号的记忆"的页面如果挨个打开 100 个库，会反复驱逐、反复建连接，
   而 SQLite 建连接要读 WAL、跑迁移检查。必须走"账号索引 → 按需打开"。
3. **鉴权粒度不够。** 上一轮审计已经发现：core 的 `require_plugin_scope`
   只判断"能不能访问这个插件"，不区分"能不能看这个 bot 的数据"。百账号场景下
   这是真实的越权面——管理员 A 不该看到 bot B 的用户记忆。

### 该怎么做（建议顺序）

1. **账号索引页**：读 `_index.json` + 各库 `stats()`，列 platform_id、记忆数、
   最后活跃、磁盘占用。不打开库（只读索引），零连接成本。这一页就能解决
   "100 个账号现在都什么状态"的运维刚需。
2. **单账号详情页**：选定 platform_id 才打开那一个库，展示常驻六席 + 记忆列表 +
   未总结消息数。天然不会超连接数。
3. **模型链与任务健康页**：`FallbackProvider.log` 已经在内存里记了最近 64 次
   调用（谁成功、谁失败、什么类别、耗时）。这是 core 有、fleet 现在只在
   `/fleet 状态` 里给一行的东西。
4. **鉴权**：按 platform_id 白名单授权，不是按插件授权。

**判断：这不是"没来得及"，是"优先级排在召回之后"。** 如果现在就要跑 100 个
账号，第 1 项（账号索引）比 3、4 项更紧急——没有它你无法知道哪个账号已经
停止记忆了。

### 已落地：账号索引页（v0.5.0）

按上面第 1 项实现，刻意**只做这一页**：

| 组件 | 行数 | 职责 |
|---|---|---|
| `packages/fleet/.../console.py` | 240 | 纯函数：过滤、排序、分页、告警分级 |
| `webapi.py` | 200 | HTTP 薄壳，只读，4 个接口 |
| `views/fleet/` | 3 文件 | 单页：列表 + 告警 + 详情抽屉 |

**关键设计：首屏不打开任何数据库连接。** 数据来自
`BotRegistry.accounts()`——纯 `os.listdir` + `os.stat`，加上内存里的
`_index.json`。实测 100 个账号首屏 **5.68ms，打开连接数 0**。

记忆条数、未总结条数必须查库，所以做成了独立的「取统计」动作：
每次最多 20 个，单库 7.6ms（20 个共 152ms），**用完立即关库**，不占 LRU。
这样「看一眼概览」永远不会把正在服务的连接挤掉。

告警分三类，都是磁盘与索引不一致时才会出现、且不会被任何流程报错的：

- `orphan`（error）：磁盘有库文件，索引里没有 platform_id。库文件是
  slug+8 位 hash，**不可逆**，所以这类数据永远读不到，只能手工处理。
- `missing`（error）：索引里有账号，库文件不见了。
- `stale`（warn）：超过 `account_stale_days` 没新数据。

**v0.5 时的缺口**：单账号详情只有抽屉里的只读展示，没有记忆列表、没有编辑、
没有删除。也就是说这一页只解决了「知道谁哑了」，没解决「哑了之后怎么办」。

### 已落地：v0.6 把内容管理补回来了

组织方式刻意**不等于** core 的 7 个 tab。百账号下「7 个 tab × N 个账号」是
双层导航地狱，而且 core 那种「一张表看全部记忆」的页面在 fleet 里要么炸连接数、
要么跨租户越权。v0.6 分成两层：

    全局层                          单账号下钻页（#/a/<platform_id>）
    ├─ 账号索引（v0.5）            ├─ 记忆：作用域 → 列表 → 编辑/软删/合并
    ├─ 模型链（新）                ├─ 常驻：六席可视编辑（按人 + 场景）
    └─ 设置（新）                  ├─ 未总结：按会话分组，看得见卡在哪
                                   └─ 操作：立刻总结

接口从 4 个（全只读）扩到 20 个：

| 类别 | 接口 |
|---|---|
| 全局 | `overview` `health` `probe` `notes` `providers` `models` `models/chain` `models/test` `config` `config/save` |
| 下钻 | `account` `scopes` `memories` `memories/update` `memories/delete` `memories/merge` `resident` `resident/save` `messages` `actions/summarize` |

几个关键取舍：

- **不跨库。** `packages/fleet/admin.py` 的所有函数只接受一个已打开的 db，
  没有「遍历所有账号」的入口。跨账号动作必须由调用方显式循环，从而继承
  `probe` 定下的 20 个上限与「用完即关」。
- **删除是软删，复用 `merged_into` 指向自身**，与 `MemoryService.forget` 同一套
  语义。物理删除只有 `purge_owner` 一个入口，删除整个账号仍然**没有** UI
  （它要删一整库用户记忆，得先有导出确认流程）。
- **搜索限定在当前作用域。** 存储的 `search_candidates` 强制 `can_read`，
  管理台没有「上帝视角」读法——这正是仍未实现的账号级鉴权缺口。以 owner
  自己视角查自己的作用域，结果完整且不越权。
- **合并走存储的 `merge()`**，所以顺手验证了「整理只写 0」那个疑点：
  手动合并一次，`merged_into` 立刻出现非零值。
- **模型链直连单个 provider 测**（绕过降级链）：从链上测只能知道「还行/全挂」，
  分不清是主模型坏了还是兜底在替它干活。

设置页直接渲染 `_conf_schema.json`（21 项，分 5 组 + 其他），写回同一份配置文件。
`needs_reload` 标出「改了要重载插件才生效」的项——除了 `memory_injection`、
`capture_messages`、`account_stale_days`，其余都在 `__init__` 里读一次就固化。

**仍未做**：按 `platform_id` 白名单鉴权（多管理员下是越权面）、删除整个账号、
批量导出、技能系统。

## 3.1 账号备注：core 没有，fleet 必须有

core 只有一个 bot，账号名就是面板里那个适配器 id。fleet 有 100 个库，文件名是
`qq-01-a1b2c3d4.db` 这种不可逆的 slug+hash，**光看 id 认不出是谁**——「哪个是
客服号、哪个是测试号」是每天都要回答的问题，而 core 从不需要回答它。

所以备注不是抄 core，是百账号场景带出来的新需求：

| 决定 | 理由 |
|---|---|
| 存 `_notes.json`，不进库 | 备注是显示层别名。进库意味着每个库都要多一张表、多一次迁移 |
| **不改文件名、不改 platform_id** | 改 id 等于换账号（记忆会「消失」）；改 hash 会让索引与磁盘对不上 |
| 允许给还没落库的账号起备注 | 「先起名、等它说话」是正常顺序；列表只按 `.db` 出行，不会凭空多一行 |
| 删号时一起清备注 | 否则同 id 重建的账号会继承一个不属于它的名字 |
| 搜索/排序都覆盖备注 | 起完名字却搜不到、按名称排了还是乱序，都是同一种「口径不一致」 |
| 告警条显示备注 | 告警上写一串适配器 id，等于让人自己去对表格 |

## 3.2 后台总结模型：从「跟着主应用走」改成「显式选」

**改之前**：`llm_provider_ids` 留空 = 跟随 AstrBot 当前对话模型。小规模省事，
但它意味着主应用换一次默认模型，**长期记忆的归纳风格就静默漂移一次**，
事后无法归因是哪次切换让记忆变了味——而记忆恰恰是「越稳定越有用」的东西。

**改之后**（`hermes_fleet/chain.py` + 管理台「模型链」页）：

- 候选**只从主应用已配置的服务提供商里选**（`context.get_all_providers()`），
  记忆系统不自己维护模型清单，也不改主应用的任何配置。
- 选定后写进本插件自己的配置，主应用换默认模型**不再影响**它。
- 主模型 + 最多 4 个降级，顺序即优先级；`__current__` 是显式写法的
  「跟随当前」，与「没配置」区分开——前者是主动选择，后者页面标警告。
- 保存时服务端校验：模型必须在主应用里存在、主模型不能同时出现在降级里、
  降级不超过 4 个。写错一个字符的代价是半夜的总结静默失败，必须当场拦住。
- 保存后**立即重建** `FallbackProvider` 并换掉 `summarizer.llm` /
  `consolidator.llm` 的引用，不需要重载插件。旧实例的冷却表一起丢弃：
  否则新选的主模型一上来就背着前一个模型的冷却。
- 拿不到候选清单时（AstrBot 未启动完）只校验格式，不锁死人的配置。

## 4. 模型路由：core 有 904 行，fleet 之前是裸调

这是本轮**真正补上的缺口**，而且是"等等"里最要命的一项。

**补之前的状态**：`AstrBotProvider` 只取一个 provider，配了 `llm_provider_id`
就锁死那一个，未加载就抛裸 `RuntimeError`。它挂掉时，落库的消息永远不再总结，
**而没有任何界面会告诉你**。单点故障在 100 个账号上被放大 100 倍。

而用户实际配置的主模型 + 回退链（deepseek-flash → glm-4.7-flash → nemotron）
在这条路径上完全没有生效——AstrBot 自己对话时用回退链，但插件后台总结不用。

**补之后**：`hermes_workers/fallback.py`

| 能力 | 实现 |
|---|---|
| 错误分类 | `classify()` 只看类名与消息文本，覆盖各家 SDK |
| 单模型重试 | 只对 `UNAVAILABLE` / `RATE_LIMITED` / `INTERNAL`，指数退避 + 抖动，单次等待硬上限 15s |
| 换模型 | 鉴权错/404/参数错**立刻换**（重试只会烧配额）；`ctx` 超长也换（大模型能扛） |
| 冷却 | 失败模型进冷却垫后；**全部冷却时仍然试一次**——后台静默不干活比撞坏模型糟 |
| 观测 | 环形日志 64 条 + `ChainStats` 计数，接进 `/fleet status` |
| 契约翻译 | 所有异常翻成 `Unavailable` / `RateLimited` / …，带 `retry_after_s` |

**与 core 的差别**：core 把"选模型、重试、裁剪 prompt、写日志"揉在一个 900 行
的类里；fleet 只做两件事——挑一个能用的 provider、把失败翻译成契约错误码。
prompt 裁剪归 worker（它知道 token 预算），日志归 `FallbackProvider`。

**刻意没做**：core 的"按目标模型上下文长度裁剪 prompt"。fleet 的 worker 目前
只用 `max_tokens` 控制输出，没有按输入上下文自适应。这在接了小上下文兜底模型
（比如 8k）时会真出问题——**这是已知缺口，不是已完成项**。

## 5. 技能系统：刻意不做

core 有 `skill_hub.py` 322 行 + `list_skills` / `read_skill` / `save_skill` /
`update_skill` 四个工具。fleet 一个都没有。

理由：技能是"让 AI 自己写代码扩展自己"，与"100 个账号各自隔离的长期记忆"
是两个正交问题。塞进来会让 fleet 的定位变模糊，而且技能执行有安全面——
百账号场景下更要谨慎。如果确实需要，应该是独立插件，通过 AstrBot 的
`llm_tool` 并存，而不是塞进 fleet 的存储层。

**这是取舍，不是遗漏。** 但如果你要的是"hermes_core 的完整替代品"，那就
是缺的——判断权在你。

---

## 6. 热重载：未做，影响小

core 的 `hot_reload.py` 155 行让插件能在改配置后不重启 AstrBot 就生效。
fleet 没做。实际影响：改 `_conf_schema` 里的值要重启 AstrBot。

考虑到降级链配置（`llm_provider_ids`）恰恰是最需要"改完立刻验证"的东西，
这个缺失比在 core 里更明显。如果要补，优先级高于 WebUI 第 3、4 项。

---

## 7. 一句话总结

- **常驻记忆：照搬了设计**，实现按一 bot 一库重写。这部分不需要重做。
- **WebUI：第一页（账号索引）已做**，按百账号重新设计而非照搬。首屏零连接，
  100 账号 5.68ms。其余页面（删除、鉴权、导出）仍未做。
- **模型路由：之前是真缺**，本轮已补，但"按上下文裁剪 prompt"仍未做。
- **技能系统：刻意不做**，属于定位取舍。
- **热重载：未做**，影响比 core 里更明显，因为降级链配置最需要即时验证。

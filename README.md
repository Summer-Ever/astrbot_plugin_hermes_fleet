# Hermes 百账号记忆（astrbot_plugin_hermes_fleet）

给**上百个机器人账号**用的长期记忆插件。每个账号一个独立的记忆库文件，
账号之间的记忆**物理隔离**——串号不是靠"记得写 WHERE"来避免，而是不可能发生。

已在 AstrBot 4.x 上按 `qq_official`（QQ 官方机器人）形态验证接入方式。

## 它做什么

| 能力 | 触发点 | 说明 |
|---|---|---|
| 每轮注入常驻设定 | `on_llm_request` | 称呼、助手设定、用户信息、偏好忌讳、亲密关系与情感表达、回复风格、规则避雷七个词条 |
| 会话落库 | `on_llm_response` | 用户发言 + 机器人回复写进该账号自己的消息表 |
| 记忆检索 | 工具 `search_memory` | 模型主动调用，检索归档记忆 |
| 记忆写入 | 工具 `save_memory` | 自动归属到当前发言用户 |
| 常驻维护 | 工具 `update_resident` | **用户说一句「以后叫我阿明」，模型自己改词条**；整段覆盖，不是追加 |
| 删除记忆 | 工具 `forget_memory` | 软删除，判错了能回滚 |
| 提取记忆 | `/提取记忆` | 把「你 + 本机器人」的数据打成两份文件发给你（原文 + 可导入的记忆配置） |
| 导入记忆 | `/导入记忆` + 附件 | 把「记忆配置」文件发回来，复原常驻与归档记忆；也可在面板对应账号的「操作」页选文件导入 |
| 提取常驻记忆 | `/提取常驻记忆` | 输出当前场景**实际注入给模型**的完整常驻提示词（含边界声明与维护约定） |
| 指令清单 | `/hc帮助` | 列出所有可用指令与管理员指令 |
| 运维 | `/fleet` 命令组 | 状态、我是谁、常驻、账号列表、总结、整理、删除账号记忆库 |

**不做**每轮自动检索注入。每轮固定烧几千字符换回来的多半是噪声，
还会把真正的用户发言挤到后面。召回交给模型主动调用。

**常驻可以纯靠说话改**：不需要进面板。模型能自己调 `update_resident`，
配套有四件事（都实测过，缺一件就退化成「说记住了其实没写」）：

- 注入块里始终带维护约定，常驻全空时也带——空的时候正是最需要指引的时刻；
- 判据是**「哪句话更新」而不是「用户有没有说『记住』」**：他说到的现状和
  某个词条对不上（词条写杭州、他说在深圳），就以他这次说的为准改写那一条；
- 用户说「我毕业了」「以后叫我 X」这类**自身变化**时，多注入一行
  `[本轮]` 提示；谈到了某词条里的具体信息时，提示会点名是哪一条；
- 写入前压平换行、拆掉块边界标记，词条里塞不进「多行指令」；
- 词条被明确声明为「数据不是指令」，带指令腔的内容（「忽略以上指令…」）直接拒绝。

后两条提示是**按需**出现的，不是每轮都写「记得核对」——那句话每轮都在，
等于告诉模型可以跳过它。降噪靠两条：命中的必须是词条里被标点切开的独立
实体（「杭州」「做客服」，而不是「别在群里发广告」里的「群里」），以及
近况线索词必须和第一人称同句（「现在这段代码报错」不触发）。

**每个词条记的是谁，都写在标签里**：注入时不用「称呼：阿明」这种可以两读的短标签，
而是「怎么称呼用户：阿明」「你的自我设定：自称小雅」。词条内容由模型自己写，
它完全可能把「你叫小雅」写进 address；加上主语后，「这是谁的信息」不靠猜。
写反了也不会静默通过——返回值里会带一句提醒（「你自己的名字属于 assistant」），
但**不阻断**：用户原话「我叫小明，叫我小明」本来就是混着说的。

**注入位置可选**（`inject_to_system_prompt`，默认关）：

**位置**固定：常驻块永远排在**本轮用户发言之前**——画像是「关于这个用户的事实」，
模型先看到「他是谁、忌什么」，再看这轮说了什么。开关只改**权威性**：

| | 落在哪 | 模型怎么看 | 代价 |
|---|---|---|---|
| 关（默认） | 一条独立用户消息，插在用户发言**之前**（发给模型，不写进对话历史） | 用户给的资料 | 「规则与避雷」只是资料，不是命令 |
| 开 | 本轮 `system_prompt` **末尾**（在所有对话之前） | 与人格设定同级的硬约束 | 词条正文可能来自历史对话（群友能写），指令腔更容易被当真 |

默认取前者：常驻的本职是**提供事实**，不是下达命令；「不许骂人、必须报价」
这类强约束本来就该写进人设。开关打开后立即生效，不用重载——两条路都不进
会话历史，区别只在权威性（系统提示词改动会让该段之后的缓存失效）。

写作 `update_resident(block, text)`：`block` 六选一，中英文都认（`address` / `称呼`）；
`text` 是**整段新文本**，空串 = 清空该词条。

## 提取记忆 / 导入记忆

对机器人发 `/提取记忆`（或 `/fleet 提取记忆`），会收到**两份文件**：

1. **hermes-memory-…（记忆配置）**——常驻记忆 + 归档记忆，人能读、
   机器也能导回去。开头有一个 `<!-- hermes-import-v1 … -->` 块，记录账号、
   用户、七个常驻词条和每条归档记忆，用于复原配置；
2. **hermes-chat-…（对话原文）**——纯文字，一条一行，带完整年月日
   `[2025-11-25 09:30:12]`，全量导出，不受条数限制。

**复原配置**：把第一份文件（记忆配置）作为附件发回机器人，附带 `/导入记忆`。
常驻按词条**整段覆盖**，归档记忆**追加**为新条目（重复导入会产生两条，
这是刻意的——追加语义可预期）。来源文档里的全局/公开记忆会被降级为本人私有，
避免一份文件就往所有人库里写东西。导入目标永远是**当前机器人账号 + 发件人**，
文档里的来源账号只作提示。

默认只导自己的。带参数 `/fleet 提取记忆 <用户标识>` 可指定他人，**仅管理员**；
普通用户带上参数只会被拒绝，不会拿到别人的任何数据。

隐私边界（有测试钉住）：

- 群会话是全体成员共享 session id 的。导出**不含其他群友的发言**，也不含
  「机器人回复别人的话」——后者是靠「上一条是谁说的」判断的，不是看
  `sender_id` 是否为空；
- 只涉及当前这个机器人账号，其他账号的数据物理上就不在同一个库里；
- 文件含聊天原文，请当私人资料处理。插件目录 `exports/` 里的副本默认
  7 天后随下次导出一起清理。

限制：两份文件合计超过 **100MB** 会提示导出失败、联系管理员（一个文件都不发，
避免出现只发一半）。部分平台不支持发送文件组件时退化为带本地路径的文本提示；
OneBot 侧需要 `file:///` URI，组件已同时带上 `url`。

## 安装

**推荐走面板**：插件 → 安装 → 填仓库地址
`https://github.com/Summer-Ever/astrbot_plugin_hermes_fleet`。装完立刻可用，不用重启，
插件列表、配置页、更新来源都会自动登记。

手工 `git clone` 到 `data/plugins/` 也能跑，但面板不会登记它（列表里看不到、没有配置页、
没有更新来源），且要重启后端。两种方式的差异见 `docs/08-本地部署记录.md`。

**零第三方依赖**，不需要 pip 装任何东西。要求 Python ≥ 3.11（用到 `X | None` 语法）
与带 FTS5 的 SQLite（标准库自带）。

## 配置

常用八项（其余见插件设置页，共 40 项）：

| 键 | 默认 | 作用 |
|---|---|---|
| `memory_injection` | 开 | 每轮注入常驻设定 |
| `inject_to_system_prompt` | 关 | 关=作为用户提示词片段；开=拼到系统提示词末尾（见上文对比） |
| `capture_messages` | 开 | 记录会话原文（后续总结的原料） |
| `bot_db_dir` | 空 | 留空用 `data/plugin_data/astrbot_plugin_hermes_fleet/bots/` |
| `max_open_bots` | 24 | 同时打开的账号库上限，超出按 LRU 关闭 |
| `recall_k` | 5 | 每次检索返回条数 |
| `group_private_memory` | 关 | 允许在群里引用本人的私聊记忆（默认关，见下文） |
| `export_enabled` | 开 | 允许 `/提取记忆` 导出、`/导入记忆` 导入；关心隐私的群请关掉 |

> 聊天原文始终**全量**导出（唯一的硬上限是单份 100MB，超了提示联系管理员），
> 没有「最多导多少条」的设置——旧版本的 `export_max_messages` 已移除。

后台任务相关的几项（其余保持默认）：

| 键 | 默认 | 作用 |
|---|---|---|
| `llm_provider_ids` | 空 | **后台总结用的模型链**，逗号分隔，第一个是主模型。建议在管理台「模型链」页直接挑，保存即生效 |
| `llm_provider_id` | 空 | 单模型配置（兼容旧版）。配了链就留空 |
| `llm_cooldown_seconds` | 180 | 失败的模型多久内排到队尾 |
| `summarize_interval_minutes` | 15 | 后台循环间隔 |
| `consolidate_min_active` | 30 | 一个作用域攒够多少条记忆才整理 |

**为什么要显式配链**：后台总结是用户看不见的。主模型挂掉时，新消息永远不再
变成记忆，而没有任何界面会报错——只会表现为"记忆怎么不涨"。AstrBot 自己的
对话走回退链，但插件的后台任务不走，除非在这里显式配。`/fleet 状态` 能看到
当前链和每个模型的冷却剩余秒数。

**为什么必须显式**（v0.7 改）：链留空时等于"跟随主应用当前对话模型"。由主应用
的默认模型决定记忆的归纳风格，意味着主应用换一次模型、记忆的味儿就静默变一次，
而且事后无法归因。候选仍然只从主应用已配置的模型里来（不自己维护清单、也不改
主应用的配置），但选定后写在本插件自己的配置里，**主应用换默认模型不再影响它**。

## 管理台

AstrBot 面板 → 插件 → Fleet 账号台。分两层：**全局三页** + **单账号下钻**。

### 全局

| 页面 | 能力 |
|---|---|
| 账号索引 | 按最后写入排序，一眼看出谁不动了；可给每个账号**起备注**（显示名）；**首屏不打开任何数据库连接** |
| 模型链 | 主模型 → 降级 1 → 降级 2 的实际顺序、谁在冷却、最近 64 次调用、逐模型测连通；**在页面上选主模型与降级，保存即生效** |
| 备份 | 一键备份整个插件的数据与设置；列出 / 下载历史备份（保留最近 10 份）；恢复（输入 `RESTORE` 确认）；回滚到恢复前快照 |
| 设置 | 直接改 `_conf_schema.json` 里的 40 项，标出「改了要重载插件」的项 |

账号索引上的动作：搜索（备注、账号 ID、文件名都命中）/ 排序、给账号起备注、
对当前页最多 20 个账号「取统计」（用完立即关库）、告警（孤立库 / 库丢失 /
静默超阈值）。

**备注**只是显示层的别名，存在该账号目录的 `bot.json` 里（v1 的 `_notes.json`
仍可读）：不改 `platform_id`（改它等于换账号，记忆会「消失」），也不改库文件名
（文件名带 hash，改了索引就和磁盘对不上）。有备注时第一列主显备注、第二行同时给
ID 与文件名；告警条上也显示备注。

同一个 `bot.json` 还存**账号描述**与**按账号覆盖的开关**
（`capture_messages` / `summarize_enabled` / `consolidate_enabled` /
`group_private_memory` / `recall_k`），优先级是「账号覆盖 > 全局配置 > 默认值」。
模型链、并发、间隔、冷却属于全局资源，不跟着账号拆——否则「为什么这个号半夜在跑」
无法归因。

「孤立库」指磁盘上有库文件但索引里没有对应账号——文件名是 slug + 8 位 hash，
不可逆，所以这类数据**任何流程都读不到**，只能手工处理。索引损坏或从别的
机器拷库过来时会出现。

静默阈值用 `account_stale_days` 调（默认 7 天）。

### 单账号下钻（点任意一行）

这一层才打开那个库，而且只开这一个。四个 tab：

| tab | 能做什么 |
|---|---|
| 记忆 | 左栏按作用域（谁 / 哪个群）选人，右栏翻页或搜索；行内编辑内容与 kind；勾选批量**合并**或**删除** |
| 常驻 | 按「人 + 场景（私聊 / 某群）」读七个词条，整段编辑后保存；「亲密关系与情感表达」只由用户用 `/fleet 修改亲密关系和情感表达 <内容>` 维护，AI 不参与。单条上限：普通词条 2000 字、亲密关系 3000 字（管理台「常驻」页可直接改，范围 100–10000，保存即生效；改小只挡新写入，不截断已存内容）；注入不再设总预算，空槽不注入 |
| 未总结 | 按会话分组列出还没被总结的消息，看得见「卡在哪个会话」 |
| 开关 | 这个账号单独覆盖：记录对话 / 后台总结 / 记忆整理 / 群内引用私聊记忆 / recall_k；留「跟随全局」即回到全局配置 |
| 操作 | 立刻总结（不看条数阈值）；**总结预览** 先看会写出哪些记忆、确认后才写库；**深度整理预览** 先看会把哪些记忆并成一条、确认后才写库 |

删除是**软删**（`merged_into` 指向自身），可回溯；物理删除整库仍然没有 UI 入口。


## 为什么每个账号一个库文件

两种隔离方式的成本不对称：

- **一个库 + `WHERE bot_id=?`**：靠每条 SQL 都记得带条件。漏一处就静默串号，
  **而且不会报错**。100 个账号、几十处查询，靠纪律守住不成立。
- **一个账号一个文件**：另一个账号的数据根本不在这个连接能看到的范围内。
  删账号就是删文件，备份就是拷文件。

实测尾延迟也是每库一文件更好（同机、总负载 200 条/秒）：

| 写者形态 | p99 |
|---|---|
| 单库 + 100 写线程 | 2288 ms |
| 单库 + 1 写线程（只按条数提交） | 517 ms |
| 单库 + 1 写线程（条数或超时双触发） | 75 ms |
| **每 bot 一库** | **7.8 ms** |

复现：`python benchmarks/bench_arch.py`。

## 数据布局与备份恢复

v2 把一个账号的**全部可搬移状态**放进一个目录：

```
<插件数据目录>/
├── layout.json                布局版本标记（读路径不看它，以文件为准）
├── _index.json                文件名 ↔ platform_id 缓存（丢了可重建）
└── bots/<stem>/
    ├── bot.json               备注、描述、创建时间、按账号开关
    └── memory.db              这个账号的全部记忆与消息
```

`<stem>` 是「slug + 8 位 hash」（如 `qq-01-a1b2c3d4`），由 `platform_id` 稳定推出。
v1 的「根目录平铺 `<stem>.db` + `_notes.json`」仍可读，首次启动幂等迁移：先
`wal_checkpoint(TRUNCATE)`（否则最近写入留在 `-wal` 里，搬完就丢）、同盘
`os.replace` 搬库、写 `bot.json`、比对各表行数；迁移前自动备份到数据目录之外的
`hermes_fleet_backups/`，任一步失败旧文件原地不动。

备份的是**整个插件的状态**：manifest + 每个账号目录（`bot.json` + `memory.db`，
逐库走 SQLite 在线备份 API，不直接拷文件）+ 配置快照
（`config/plugin_config.json`）。落点在 `plugin_data` 之外
（`<AstrBot data>/hermes_fleet_backups/`），误删/卸载插件不会连带删掉备份；
保留最近 10 份，同名同秒追加序号。

恢复是两阶段的，**只读预检全部通过才动手**：zip 结构与路径穿越、条目体积与压缩比、
逐文件 sha256、解出后 `integrity_check`、库版本降级（备份比本机新则拒绝）。通过后
先打一份 `hermes-pre-restore-*.zip` 快照（失败即中止，不动任何文件），在数据目录
同盘解压，`close_all()` 之后整目录 `os.replace` 换入，任一步失败按撤销日志回滚。
恢复旧包只替换包内账号，备份之后新建的账号目录保持不动；恢复配置时强制保留本机的
`bot_db_dir`，需要重载的键会在结果里提示。

## 「是哪个账号」怎么取

```python
event.get_platform_id()   # -> 面板里给每个适配器配的 id，如 "qq-01"
```

依据是 AstrBot 的适配器元数据：`PlatformMetadata.id` 取自每个适配器配置的
`id` 字段，`qq_official` 适配器同样如此（`id=cast(str, self.config.get("id"))`）；
`get_platform_id()` 的注释也写明"同时运行多个同类型适配器时 ID 唯一"。
所以一个 AstrBot 实例里配 100 个 QQ 官方机器人，插件能直接分辨是哪一个，
**不需要改本体、不需要打补丁**。

文件名会带 8 位 hash 后缀：`qq-01` 与 `qq_1` 若只做字符替换会折叠成同一个
文件，两个号共用一个记忆——这类事故是静默的。

## 隐私边界

- **私聊与群聊的常驻是两套**：`private` 与 `group:<gid>` 分开存，私聊设定不会
  在群里生效。
- **群里不引用私聊记忆**：`group_private_memory` 默认关闭。`can_read` 里
  "owner 相同即可读"在私聊是对的，但群里把私聊内容念出来就是当众公开。
- **群记忆不外溢**：在 A 群存的事，B 群检索不到；**私聊也不召回群记忆**，
  哪怕是自己说的——私聊与群聊是两套上下文。
- **群里默认只记自己的**：`group_memory_shared` 默认关闭。同群别人说过的归档
  记忆不参与你的检索——「别人说的话被机器人当成你的记忆复述」既像串号也像
  泄密。确实要团队共享时，在管理台按账号打开；它不会突破跨群与私聊边界。

## 向量召回（可选）

默认关闭。开启后：字面检索（FTS + 混合粒度 BM25 精排）**凑不满** `recall_k`
时，用 embedding 按余弦相似度补齐；字面检索够用时输出与经典档完全一致。

**为什么是「补齐」而不是「并池后再精排」**：精排用 BM25 打分，与问句没有
任何字面交集的候选会得 0 分并被直接丢弃——而向量要解决的恰恰是「词汇鸿沟」。
并进候选池等于白做一次昂贵的向量查询。所以向量只补字面链路给不满的名额，
且永远排在字面命中之后（顺序沿用 docs/06 的评测结论）。

**存什么**：只存归档记忆条目的向量，不存原始对话、不存常驻词条。图片 / 视频 /
文档本来就不入库（只落 `event.message_str`），所以也不会进向量库——没有二进制、
没有附件解析、没有额外隐私面。

**存在哪**：每个账号目录下的 `vectors.db`（与 `memory.db` 同目录）。

- `memory.db` 是唯一真相；向量删了 / 坏了 / 换模型，重建即可；
- 备份包只收 `memory.db` + `bot.json`，**不含** `vectors.db`，恢复到另一台
  机器不会带回旧向量；`/提取记忆` 也只导出记忆与原文；
- 体积估算：1024 维 float32 ≈ 4KB/条，1 万条 ≈ 40MB/账号。嫌大可把
  `vector_dim` 降到 512，或只给需要的账号开向量检索。

**怎么接模型**：`vector_provider=api` + `vector_base_url` + `vector_model`。
OpenAI 兼容的 `/embeddings` 都能用（OpenAI、硅基流动、百炼、Ollama `/v1`、
vLLM）。插件**不引入** onnxruntime / fastembed 这类原生依赖——装不上会连插件
一起加载失败；要本地模型，起一个 Ollama/vLLM 再指向它即可。

**成本与延迟**：每条记忆只在新增 / 改写 / 合并后各向量化一次（后台按
`content_hash` 差集增量，默认 5 分钟一轮、每账号每轮最多 256 条）；查询侧每次
检索最多一次 embedding 调用，45 秒内同一句查询命中缓存。并发检索**不是各调一次**：
查询先进入有界队列（上限 256），由 2 个 worker 攒 10ms 窗口合批，同一批里重复的
问句只算一次。每个请求最多等 `vector_query_timeout_seconds`（默认 2 秒），超预算
或队列满就少补几条语义记忆、直接用字面结果；embedding 失败也一样——不会让用户
等，也不会把错误抛给模型。

| 键 | 默认 | 说明 |
|---|---|---|
| `recall_mode` | `classic` | 默认档；按账号可在管理台覆盖为 `vector` |
| `vector_provider` | `off` | `off` / `api` |
| `vector_model` | 空 | 留空等于不启用 |
| `vector_min_score` | 0.35 | 语义补齐的最低余弦相似度 |
| `vector_query_timeout_seconds` | 2 | 单次检索等待向量化的预算，超时退回字面召回 |
| `vector_sync_minutes` | 5 | 后台增量索引间隔 |
| `vector_dim` | 0 | 0 = 由服务返回决定 |

**管理台**：单账号「操作」页有索引状态（模型 / 已索引 / 活跃 / 待索引 /
最后同步 / 最近错误）与「重建 / 清除」。重建按批返回，剩余由后台继续。

**性能**：`python tools/bench_vector.py` 生成 1k / 10k / 100k 条合成向量，
测精确 KNN 的 p50 / p95、50 并发与事件循环延迟。本机实测（无 numpy、256 维）：
单次检索 p50 ≈ 20ms、p95 ≈ 22ms（只扫最近约 2k 条窗口）；50 个并发检索总耗时
约 1.6s，事件循环最大卡顿 27ms。装了 numpy 后走矩阵乘，10 万条全库精确检索是
毫秒级，并发不再被「Python 循环逐条点积」的 GIL 拖住——**生产建议装 numpy**。
不装也能用，但语义补齐只发生在一个最近窗口内，超出部分仍由字面召回兜底。

真正的并发瓶颈不是 KNN，而是 embedding 调用本身（网络/服务端）。向量检索只在
模型主动调 `search_memory` 时发生，不是每轮对话都调；接云端 API 还是本地
Ollama/vLLM 取决于你的 QPS 与预算，插件侧只认 OpenAI 兼容协议。

## 压力测试（等价环境）

`benchmarks/bench_fleet_load.py` **不起 AstrBot**，直接按 `main.py` 的调用顺序跑
`hermes_fleet`：身份解析 → 注入 → 检索 → 落库 →（可选）真实总结 / 向量索引。
压的是记忆插件本身，而不是宿主的网络栈；并发出问题还会自动做跨账号、跨用户、
群/私聊隔离探针。

```bash
# 离线：20 个账号 × 20 个用户（400 个并发会话）
python benchmarks/bench_fleet_load.py --bots 20 --users-per-bot 20

# 接本机正在用的总结模型（读 AstrBot 配置里的模型链）
python benchmarks/bench_fleet_load.py --llm auto \
    --llm-model 阿里云/qwen3.7-flash --summarize-bots 1

# 接真实 embedding（自动探测 OpenAI 兼容端点）
python benchmarks/bench_fleet_load.py --embed auto \
    --vector-bots 2 --vector-concurrency 6

# 本机 CPU 跑本地模型（transformers + torch，不需要任何外部服务）
python benchmarks/bench_fleet_load.py --embed local \
    --vector-bots 2 --vector-concurrency 8 --embed-threads 4
```

`--llm fake|auto|off`、`--embed fake|auto|local|off` 可切换；密钥只用于请求，
不写进报告。`HERMES_BENCH_LLM_*` / `HERMES_BENCH_EMBED_*` 可覆盖自动探测。
`--embed local` 默认用 `BAAI/bge-small-zh-v1.5`（512 维、24M 参数），首次运行会
从 HuggingFace 下载约 95MB 权重。

本机实测（单进程、单核）：

| 场景 | 吞吐 | 单条 p95 | CPU | 说明 |
|---|---:|---:|---:|---|
| 400 用户，1 轮 / 1.5s | 1,087 ops/s | 检索 1.4ms · 落库 0.24ms | 34% | 余量充足 |
| 1000 用户，1 轮 / 1.5s | 2,171 ops/s | 检索 1.9ms · 落库 0.5ms | 111% | 单核饱和 |
| 真实 qwen3.7-flash 总结 | — | 25s / 会话 | — | 1 个会话产出 8 条记忆 |
| 真实 text-embedding-v4 | 5.6 条/秒 | 查询 265ms | 7% | 1024 维，单批上限 10 |
| 本地 bge-small-zh，100 用户 | 278 ops/s | 检索 10.9ms | 366% | 512 维，RSS 509MB |
| 本地 bge-small-zh，400 用户（合批前） | 1,001 ops/s | 检索 1.1s | 1,070% | 每次检索各调一次模型 |
| 本地 bge-small-zh，400 用户（合批后） | 1,082 ops/s | 检索 64.8ms | 1,185% | 查询进有界队列合批 |
| 本地 bge-small-zh，800 用户（合批后） | 1,400 ops/s | 检索 2.5s | 239% | 0 错误；尾部来自事件循环卡顿 |

本地向量与云端的差别（同一批记忆、12 条改述问句）：

| | 单条延迟 | 索引吞吐 | 召回 top1 / top3 | 内存 |
|---|---:|---:|---:|---:|
| 云端 text-embedding-v4（1024 维） | 265ms | 5.6 条/秒 | 11/12 · 11/12 | 0 |
| 本地 bge-small-zh（512 维，CPU） | 4.9ms | 383 条/秒 | 9/12 · 12/12 | ~460MB |

结论：**记忆插件本身不是瓶颈**（检索与落库都在毫秒内），瓶颈是单进程 CPU
与 embedding 网络往返。1000 个持续发言的用户会吃满一个核；上千用户应多进程 /
多 worker 部署。向量检索在字面召回不足时会多一次 embedding 调用（约 250ms），
只影响模型主动调 `search_memory` 的那一轮，不是每轮对话。

本地向量是「省钱、快、但有硬上限」：单实例 CPU 推理约 200 条/秒（空载），
合批后 400 个用户仍能把检索压在几十毫秒；到 800 个用户时吞吐还在涨（1,400
ops/s）、错误为 0，但尾部会到秒级——这部分不再是模型，而是事件循环本身会出现
几百毫秒到两秒的卡顿（把向量关掉、只提高单账号写入密度也能复现），属于存储层
的独立问题，不要算在 embedding 头上。所以 CPU 机器上开向量档要按账号限量，
成百上千活跃用户请走云端或多机分摊。核显并没有优势——短文本下驱动与显存拷贝
的开销盖过算力，而且核显共享系统内存，内存紧张时只会更容易触发换页。

## 自动总结怎么工作

```
会话消息（已落库）
   ↓ list_pending_sessions：按「最久没动静」排序
   ↓ 够 8 条 或 超 6 小时
   ↓ 拼转录（过滤注入、压平昵称换行）
模型 → JSON 数组
   ↓ 归属校验：私聊强制归本人；群里模型写的 owner 必须在场，否则降级为群记忆
   ↓ 内容去重：同内容已存在则跳过
写 memories → 标记消息已总结
```

三条保护是**用测试固定下来的**，不是注释里的承诺：

| 情况 | 行为 | 为什么 |
|---|---|---|
| 模型调用失败 | 不标记，下轮重试 | 标记了就等于永久丢弃唯一原始素材 |
| 输出被截断 | 不解析、不标记 | 半截 JSON 会把下半条记忆写成一条 |
| 输出是 `[]` | 标记 | 否则「确实没什么可记」会每轮重烧一次模型 |

称呼与叫法不进归档层：提示词明确要求模型不输出，解析时还有一道兜底过滤。
称呼只由常驻词条的 `address` 层维护（用户说「以后叫我阿明」时模型自己改），
两边都存会出现两份互相冲突的画像。

想立刻验证模型链通不通，用 `/fleet 消息总结为记忆`（管理员），不必等 15 分钟。

## 整理怎么工作

```
某个作用域（你的私聊 / 某个群）攒够 30 条
   ↓ list_scopes：一次 group by 数出「哪些作用域值得整理」
   ↓ list_active：取最近 200 条
本地配对（bigram Jaccard，只召回候选，不决定）
   ↓ 并查集分组，每组 2～6 条，最多 8 组
模型 → JSON（keep / merge / content）
   ↓ id 白名单：只接受真的列进提示词的那些编号
   ↓ 改写表述 + 软删除（merged_into）
```

**为什么本地只做召回**：实测记录在 `pairing.py` 的注释里——「喜欢喝乌龙茶」
与「喜欢喝龙井」的相似度是 0.444，「喜欢喝乌龙茶」与「爱喝乌龙茶」也是 0.444。
纯字面分不开「换动词」和「换宾语」，所以字面只用来看候选，判断交给模型。
阈值取 0.40 而不是 0.5：漏掉一个真重复是静默的，多给模型一条候选只是多几个 token。

四道刹车（都有用例）：

| 刹车 | 作用 |
|---|---|
| 每轮每作用域最多合并 20 条 | 模型偶尔把整库判成重复 |
| id 白名单 | 模型写出没列给它的编号时，拒绝执行 |
| 条数未增长则跳过 | 模型说「保持分开」时条数不变，否则每轮重烧一次钱 |
| 合并是软删除 | 判错了能回滚（`merged_into` 指回原条） |

已知天花板：换掉全部字面用词的复述配不上对（「希望被称为哥哥」↔「希望助手称呼他为哥哥」
实测 0.357）。这条以**通过**的形式固化在测试里，接上向量召回后它会变红——
那一下就是配对能力升级完成的信号。

手动清一遍现有重复：`/fleet 整理`（管理员）。
